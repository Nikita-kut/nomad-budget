# Решения

Зафиксированные продуктовые и технические решения. Новое решение — новый пункт; отмена — пункт «заменяет D-…». UI-правила — в [UI_RULES.md](UI_RULES.md), устройство кода — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Деньги и месяц

**D-01. Три кармана.** Каждый счёт — «На жизнь», «Копилка» или «Подушка» (`AccountRole`). Всё, что пришло в подушку, — «Отложено» («Себе»); всё, что ушло из неё, «Отложено» уменьшает. Копилка копит на крупную регулярную трату и платит её сама.

**D-02. Месяц бюджета ≠ день зарплаты.** Граница месяца — `period_start_day` (1–28, по умолчанию 1-е) из настроек пользователя. Дни дохода (`income_days`) — необязательный список только для подсказок: дохода может не быть, он может приходить несколько раз в месяц. Месяц по дням дохода не делится.

**D-03. Уравнение месяца.**
`доход по плану + остаток с прошлого месяца = кредиты + взносы в копилки + конверты + «Себе» + не распределено`.
«Можно ещё потратить» = план по конвертам − потрачено по конвертам; остаток на него не влияет.

**D-04. Остаток с прошлого месяца** — сумма счетов «На жизнь» на первый день месяца в базовой валюте (`MonthModel.carryOver`). Не хранится, а каждый раз считается из операций: правка прошлого месяца задним числом сразу меняет остаток. Копилки и подушка в остаток не входят.

**D-05. Незапланированный доход** записывается обычной операцией «Доход». В текущем месяце он виден как «без плана» и не меняет «Не распределено»; если его не потратить, он приходит в следующий месяц через остаток (D-04).

**D-06. Базовая валюта — RUB.** Счета могут быть в любой валюте, итоги, план и капитал — в рублях. Колонка `user_settings.base_currency` заведена, другая база — отдельная задача: выбирается один раз при онбординге, смена = новый аккаунт.

## Честные цифры

**D-07.** История капитала — только активные счета и только с начала учёта (первая операция по активному счёту). Архивные счета импорта в капитал не входят.

**D-08.** Корректировки остатков (системные категории) не считаются ни доходом, ни расходом в графиках и итогах.

**D-09.** Средние «за N месяцев» — только по закрытым месяцам. Для темпа и «обычных расходов» — медиана, не среднее.

**D-10.** Месяцы без дохода не показываются в доле отложенного; шкала доли ограничена ±100 %. «План и факт» — только месяцы, где был план.

**D-11.** Курсы мелких валют показываются за 10ⁿ единиц (`MoneyFormat.quoteUnit`), чтобы значение было ≥ 1. Изменение курса — в процентах к предыдущему дню.

## Пользователи и доступ

**D-12. Доступ по приглашениям.** Открытая регистрация выключена (`disable_signup`), пользователей добавляет владелец. Регистрация в приложении — отдельная фаза со своим SMTP.

**D-13. Настройки пользователя** — таблица `user_settings` (начало месяца, дни дохода, база, подушка, доходность, `onboarded_at`). Тема — свойство устройства, хранится локально.

**D-14. Новый пользователь** проходит онбординг: месяц и доход → валюты → счета → категории → остатки. Стартового набора данных при регистрации нет, только системные категории корректировок.

**D-15. Данные на устройстве привязаны к пользователю** (`UserScopedStore`, префикс `u:<uid>:`): кеш, очередь неотправленных операций и черновики другого пользователя недоступны.

**D-16. Валюты добавляются по коду ISO 4217** через `ensure_currency` (белый список); курс подтягивает ежедневный cron.

## Интерфейс и производительность

**D-17.** Графики — свои, на Canvas (`presentation/charts/Charts.kt`). Сторонняя библиотека графиков перестраивала раскладку на каждом кадре и давала рывки при прокрутке.

**D-18.** Прокручиваемые экраны держат соседние элементы собранными (`LazyLayoutCacheWindow` в `CenteredLazyColumn`).

**D-19.** Открытый раздел запоминается и восстанавливается после перезагрузки страницы.

**D-20.** Дизайн: светлая и тёмная темы на холодной палитре с синим акцентом, шрифт Inter, иконки Lucide, главная плитка экрана — с градиентом. Правила — UI_RULES.

## Публичный репозиторий

**D-21.** В коде, миграциях, документации, тестах и примерах нет стран, городов, местных валют и банков владельца. Примеры — только RUB и USD. Демо-данные вымышленные (валюта XTS).

**D-22.** Без комментариев в коде; обоснования — в этом файле, в PR и в UI_RULES.

**D-23.** Правила, которые можно проверить автоматически, проверяет `tools/check_rules.sh` в CI. Новое правило — сразу и в документ, и в скрипт.

## Слежение за курсом банка

Подробности — [BANK_RATE_WATCH.md](BANK_RATE_WATCH.md).

**D-24. Слежение общее, пара — в данных.** Код умеет «следить за курсом провайдера для любой пары валют»: провайдер задан идентификатором (`tbank`), пара лежит в строке `rate_watches` владельца. Сигналы считаются по курсу обмена в приложении; курс оплаты картой только показывается строкой в сообщениях и на плитке (колонка `category` оставлена для совместимости и не используется). В коде, тестах, демо и документации — только RUB, USD и XTS (D-21).

**D-25. Канал — Telegram-бот, подписчики ≠ пользователи.** Подписка по deep link `t.me/<бот>?start=<link_code>` из приложения; подписчику не нужен аккаунт. Подписчики принадлежат слежению владельца, он видит и отключает их в приложении. Имя бота воркер кладёт в `bot_info`, токен живёт только в секретах GitHub Actions.

**D-26. Сигнал — окно, а не изменение (заменяет «три сигнала»: цель, скачок, сводка).** Задача слежения — поймать каждое выгодное окно для обмена без шума. Выгодно = курс обмена в верхних 15 % замеров за 7 дней и разница с ЦБ (`банк / ЦБ − 1`) уже медианной за те же 7 дней. На окно — одно сообщение; пока окно длится, повтор только при улучшении на 0,5 % к курсу из последнего сообщения; закрытие окна — молча. Зеркально: курс в нижних 15 % — одно предупреждение «сейчас не меняй», повтор только при ухудшении на 0,5 %. Строгость (`good_percentile`) и порог повтора (`improve_percent`) настраиваются. Сигнал «скачок» удалён в обе стороны, колонка `jump_percent` оставлена только для старых клиентов. Пока замеров меньше, чем за два торговых дня, окон нет («копим историю»). За проверку — не больше одного сообщения: сводка, иначе цель, иначе окно.

**D-27. Окно отправки и одна сводка.** Сообщения уходят только внутри окна по часовому поясу слежения, по умолчанию 10:00–18:00 `Europe/Moscow`; пояс задаётся в настройках, а не берётся из браузера. Хранится как `quiet_to` (начало окна) и `quiet_from` (конец). Отдельной ночной сводки нет: раз в день (по умолчанию в 10:00, и в выходные тоже) уходит одно сообщение — курс обмена, строка про карту, ЦБ и разница, место среди замеров недели, вердикт «выгодно / обычно / не меняй» и одна строка о том, что было вне окна отправки (18:00–19:00 и изменения выше цели). Когда биржа закрыта, вердикт — «биржа закрыта, курс выходного дня» и сравнения нет. Час сводки обязан быть внутри окна (constraint в базе, проверка в приложении).

**D-28. Проверка в облаке, снимки общие.** Воркер `tools/rates/bank_watch.py` (stdlib) запускается из GitHub Actions каждые 15 минут, Mac владельца не нужен. Снимки курсов — общая таблица `bank_rate_snapshots` (пишет сервисный ключ, читают все), хранятся 180 дней; приложение читает их через почасовую вьюху. TLS провайдера проверяется по бандлу Минцифры из `tools/rates/ca/`, только для хоста провайдера; промежуточный сертификат истекает 06.03.2027. Формат чисел в сообщениях повторяет `MoneyFormat` (D-11) и закреплён тестами с обеих сторон.

**D-29. Статистика и окна — только в часы биржи.** Вечером и в выходные у банка «ночной» курс, поэтому процентиль, медиана разницы и сами окна считаются только по снимкам, сделанным в часы торгов валютного рынка: будни 10:00–19:00 `Europe/Moscow`, без выходных и неторговых дней из таблицы `exchange_holidays` (ведётся по торговому календарю биржи, обновляется раз в год). Часы лежат в слежении (`trade_from`, `trade_to`). Снимки пишутся круглосуточно ради графика и помечаются `in_hours`; приложение и воркер фильтруют по этому флагу. Вне часов биржи окна не открываются, поэтому падение курса в 19:00 и утреннее восстановление сигналов не дают.

**D-30. Цель — отдельное правило «всегда сообщать».** Цель необязательна. Если она задана и курс обмена не ниже неё, сообщение уходит на каждой проверке, где курс изменился к прошлой проверке (в любую сторону); без изменения — тишина, ниже цели — молча прекращается. Правило не зависит от процентиля, разницы с ЦБ, разогрева и часов биржи, но соблюдает окно отправки: вне его изменения попадают в строку сводки «выше цели было: макс X». Сообщение о цели в ту же проверку заменяет сообщение об окне.

## Траты в валюте

**D-31. Траты в валюте — по средней стоимости купленной валюты.** Рублёвая сумма траты с валютного счёта — это не курс таблицы, а то, во сколько рублей обошлась валюта на этом счёте (скользящая средняя стоимость). Не хранится, а считается из всей истории операций (`CostBasisCalculator`), как остаток в D-04: правка обмена задним числом сразу меняет более поздние траты. В базе по-прежнему лежит `amount_base` по курсу таблицы на день операции — запасное значение, когда курсов нет совсем.
- По каждому счёту не в базовой валюте ведётся пара «единицы, рублёвая стоимость». Операции идут по дате; внутри дня — доход, обмен из рублей, обмен из валюты, перевод, расход, затем по `id` (времени создания у операции нет, а валюту обычно покупают и тратят в один день).
- Обмен на счёт добавляет полученные единицы по стоимости отданного: рубли — точная сумма, другая валюта — средняя стоимость отданных единиц на счёте-источнике (с него они списываются вместе со стоимостью). Обмен валюты в рубли стоит полученные рубли.
- Перевод между счетами переносит единицы вместе с пропорциональной стоимостью.
- Доход в валюте, корректировки остатка и начальный остаток счёта добавляют единицы по курсу таблицы на свой день (начальный остаток — на день первой операции по счёту): последний курс не позже этой даты, иначе текущий курс таблицы. Сам доход остаётся в рублях по курсу своего дня, не по средней стоимости.
- Расход, перевод и обмен со счёта списывают единицы по текущей средней стоимости; рублёвая сумма расхода = единицы × средняя стоимость. Если единиц на счёте нет (обменов не было, счёт в минусе), расход считается по курсу таблицы на день операции; если единиц хватает только на часть — часть по средней стоимости, остаток по курсу таблицы. Пополнение счёта в минусе сначала закрывает минус, стоимость получает только остаток.
- Счета в рублях не затрагиваются. Валюта без единого курса в расчёт не входит: остаётся сохранённый `amount_base`.
- Все экраны и выгрузка в CSV читают уже пересчитанные операции (`HomeState.transactions`); исходные лежат в `HomeState.rawTransactions`, с ними работают только действия записи. «Твой курс против таблицы» в обменах считается из сумм обмена и от средней стоимости не зависит.

## Бот

**D-32. Часы биржи и сводка — с минутами (дополняет D-27 и D-29).** По замерам банк переходит на дневной курс между 10:00 и 10:15, на ночной — между 18:45 и 18:51. Статистика и окна считаются в 10:30–18:30 МСК (`trade_open`, `trade_close` в минутах), сводка уходит в 10:30 (`digest_at`) и называется «курс на начало торгов». Разогрев называется «мало данных для сравнения», без счётчика замеров. Строка «Картой выгоднее на X %» из сообщений убрана: днём разница — доли процента, а ночью она вводила в заблуждение; курс карты остаётся на плитке в приложении.

**D-33. Мгновенные команды через вебхук.** `/rate` и любой текст отвечают текущим курсом, `/start`, `/stop`, `/help` — как раньше. Отвечает Edge Function `telegram-webhook` прямо в теле ответа вебхука, без токена бота; текст ответа готовит воркер (`state.now_text`), поэтому форматирование чисел остаётся в одном месте (D-28). Без секрета вебхука воркер продолжает читать `getUpdates` раз в 15 минут.

**D-34. Сводка, сигналы и ответ на /rate — виджеты Telegram.** Виджет (`sendWidget`, Bot API 10.4): курс крупно, цветная плашка вердикта, полоса «хуже ↔ лучше» с местом среди замеров недели, график и строка ЦБ. График недели — одна сплошная линия по торговым дням, без разрывов на ночи; у сигналов и /rate — сегодняшний день, вечерний участок закрашен. Цвет линии — направление за период: рост зелёный, падение красный, изменение меньше 0,1 % серое; вертикальный масштаб не меньше 1 % курса, чтобы десятые доли не выглядели обвалом. Разница с ЦБ зелёная, если лучше медианы недели, красная — если хуже. Цвета текста и фона — из темы чата (`--tg-theme-*`). Подпись под виджетом — одна строка с курсом и вердиктом, её же видят клиенты без виджетов. Если Telegram не принял виджет, уходит прежний текст, а `state.widgets_ok = false`; мгновенный ответ на /rate шлёт виджет, только когда воркер уже успешно отправил хотя бы один (`widgets_ok = true`), иначе текст. Цель 🎯, подписка и справка — обычным текстом. Ограничения Telegram: виджет нельзя переслать, в проде — только личные чаты.
