# Слежение за курсом банка

Приложение следит за курсом обмена банка по одной валютной паре и присылает сигналы в Telegram. Цель — поймать каждое выгодное окно для обмена и не шуметь. Проверка идёт из облака (GitHub Actions) каждые 15 минут, устройство владельца не нужно. Решения — [DECISIONS.md](DECISIONS.md), D-24…D-30.

## Как это работает

```
GitHub Actions (cron */15)                 Supabase                         Приложение
tools/rates/bank_watch.py ──курс банка──► bank_rate_snapshots ◄──читает──── экран «Курсы»
            │             ──курс ЦБ────► (общая таблица)                     плитки, график,
            │                                                                 карточка Telegram
            ├──читает───► rate_watches (настройки, state) ◄──пишет──────────┘
            ├──читает/пишет► telegram_subscribers
            ├──пишет─────► bot_info (username бота, offset getUpdates)
            └──sendMessage──► Telegram ──► подписчики
```

1. Воркер берёт все включённые `rate_watches`, группирует по провайдеру и паре, запрашивает курс банка и курс ЦБ.
2. Каждая проверка пишет снимок в `bank_rate_snapshots` для категорий «обмен в приложении» и «оплата картой» — круглосуточно, для графика. У снимка есть флаг `in_hours`: сделан ли он в часы биржи. Снимки старше 180 дней удаляются.
3. Для каждого слежения считаются сигналы и обновляется `rate_watches.state`: последний курс, открытое окно (`window`: вид, курс в последнем сообщении), события вне окна отправки для сводки (`notes`), дата последней сводки.
4. Сообщения уходят всем подписчикам слежения. Подписчики попадают в `telegram_subscribers` через deep link `t.me/<бот>?start=<link_code>`, аккаунт в приложении им не нужен.
5. Приложение показывает последний курс банка с вердиктом («выгодно / обычно / не меняй») и местом среди замеров недели, курс ЦБ с разницей и её медианой за неделю, цель, график «банк и ЦБ» по часам за 30 дней и список подписчиков. Вердикт считает `BankRateAnalyzer` по тем же правилам, что и воркер.

## Сигналы

Сигналы считаются по курсу обмена (`DebitCardsTransfers.buy`, сколько TO за 1 FROM). Курс оплаты картой в сигналах не участвует, он только показан строкой в сообщениях: «Картой выгоднее на X %» или «Картой хуже на X %».

| Сигнал | Условие | Частота |
|---|---|---|
| Выгодное окно 🟢 | курс лучше `good_percentile` % замеров за 7 дней (по умолчанию 85, то есть верхние 15 %) **и** разница с ЦБ уже медианной за 7 дней | одно сообщение на окно; пока окно длится, повтор только если курс вырос на `improve_percent` % (по умолчанию 0,5) к курсу из последнего сообщения |
| Плохое окно 🔴 | курс хуже `good_percentile` % замеров за 7 дней (нижние 15 %) | одно сообщение «сейчас не меняй»; повтор только если курс упал ещё на `improve_percent` % к прошлому предупреждению |
| Выше цели 🎯 | задана цель и курс ≥ цели | каждая проверка, на которой курс изменился к прошлой проверке (вверх или вниз), пока он не ниже цели; курс не изменился — сообщения нет; упал ниже цели — молча прекращается |
| Сводка ☀️ | первая проверка в час `digest_hour` | раз в сутки, в том числе в выходные |

Определения:

- **Замеры недели** — снимки курса обмена за последние 7 дней с `in_hours = true`. Процентиль и медиана считаются только по ним.
- **Место среди замеров** — доля замеров недели строго ниже текущего курса («лучше N % замеров недели») и строго выше него («хуже N %»). При ровном курсе всю неделю окна не открываются.
- **Разница с ЦБ** — `банк / ЦБ − 1`. Отрицательная разница — банк даёт меньше официального курса. «Уже» значит ближе к выгоде клиента: текущая разница больше медианы недели. Если курса ЦБ нет, условие по разнице пропускается.
- **Окно** — подряд идущие проверки в часы биржи, на которых условие выполняется. Закрытие окна сообщением не сопровождается. Вне часов биржи окна не открываются, а открытое закрывается: вечернее падение курса и утреннее восстановление сигналов не дают.
- **Разогрев** — пока замеров недели меньше, чем за два торговых дня (2 × часы биржи × 4 проверки в час, по умолчанию 72), выгодных и плохих окон нет, а сводка пишет «копим историю: N замеров».
- **Цель** необязательна и работает отдельно от окон: не зависит от процентиля, разницы с ЦБ, разогрева и часов биржи. Сообщение: «🎯 Курс выше цели 305: 306,10 (было 305,40)».

За одну проверку слежение отправляет не больше одного сообщения: сводка важнее цели, цель важнее окна. Если окно открылось в ту же проверку, что и сводка или сообщение о цели, отдельное сообщение об окне не уходит, а окно считается объявленным (повтор — только при улучшении). В сводке при курсе не ниже цели есть строка «Выше цели X».

Резкое изменение курса между проверками само по себе не сигнал: сигнал «скачок» удалён.

### Сводка

Одно сообщение в `digest_hour` (по умолчанию 10:00), оно же заменяет прежнюю ночную сводку:

```
☀️ RUB → USD, 10:00 · выгодно
Обмен: 100 RUB = 1,21 USD
Картой хуже на 0,8 %
ЦБ: 100 RUB = 1,25 USD · разница −3,2 %
Лучше 92 % замеров недели
Вне окна отправки: было выгодно, до 1,22
```

Вердикт: «выгодно», «обычно», «не меняй», «копим историю: N замеров». Если в момент сводки биржа закрыта, вердикт — «биржа закрыта, курс выходного дня» (выходной или неторговый день) или «биржа закрыта, ночной курс» (торговый день, но вне часов биржи), и курс ни с чем не сравнивается. Последняя строка появляется, только если вне окна отправки что-то было: открывалось выгодное или плохое окно (с лучшим и худшим курсом) или курс менялся выше цели («выше цели было: макс X»).

## Часы биржи

Вечером, ночью и в выходные банк ставит «ночной» курс с широким спредом; сравнивать его с дневным бессмысленно. Поэтому статистика и окна живут только в часы торгов валютного рынка Московской биржи:

- будни, 10:00–19:00 по `Europe/Moscow`: основная сессия с 10:00, расчёты TOM/SPT до 19:00 — [раздел валютного рынка](https://www.moex.com/ru/markets/currency), FAQ «В какое время проходят торги»;
- суббота и воскресенье — торгов нет;
- неторговые дни по [торговому календарю биржи](https://www.moex.com/ru/tradingcalendar) — таблица `exchange_holidays(date)`.

Часы хранятся в слежении: `trade_from` (по умолчанию 10) и `trade_to` (по умолчанию 19), интервал `[trade_from, trade_to)`, всегда по времени биржи, а не по поясу слежения.

Флаг `bank_rate_snapshots.in_hours` ставит воркер при записи снимка: торговый день и час внутри часов слежений этой пары (если слежений несколько — от самого раннего начала до самого позднего конца). В базе у колонки есть значение по умолчанию `exchange_in_hours(now())` со стандартными часами 10–19. Смена часов в настройках старые снимки не перемечает.

**Список неторговых дней нужно обновлять раз в год.** В миграции `0015_watch_windows.sql` заведён 2026 год: 01.01, 02.01, 07.01, 23.02, 09.03, 01.05, 11.05, 12.06, 04.11, 31.12. Когда биржа публикует календарь на следующий год, даты добавляются новой миграцией или запросом `insert into public.exchange_holidays (date) values ('2027-01-01'), …;`. Рабочие субботы, если биржа их объявит, таблица не описывает: суббота для слежения всегда неторговая.

## Окно отправки

Сообщения уходят только в окне отправки по часовому поясу слежения: по умолчанию с 10:00 до 18:00, `Europe/Moscow`. Пояс — любой идентификатор IANA, задаётся в диалоге настройки; неизвестный пояс воркер считает как `Europe/Moscow`. В базе окно хранится как `quiet_to` (начало окна) и `quiet_from` (конец окна): всё вне `[quiet_to, quiet_from)` — тишина. Одинаковые значения — присылать круглосуточно.

События в часы биржи, но вне окна отправки (по умолчанию 18:00–19:00), и изменения курса выше цели вне окна отдельно не отправляются: воркер копит их в `state.notes` и добавляет одной строкой в следующую сводку. Если сводка выключена, такие события не сохраняются. Если окно отправки начинается позже часов биржи и выгодное окно к этому моменту ещё открыто, сообщение о нём уходит на первой проверке внутри окна отправки. Час ежедневной сводки должен быть внутри окна (проверяется и в приложении, и constraint в базе).

## Провайдер `tbank`

Публичный API без авторизации: `GET https://api.tinkoff.ru/v1/currency_rates?from=<FROM>&to=<TO>`. Ответ: `payload.rates[]`, у каждого элемента `category`, `fromCurrency.name`, `toCurrency.name`, `buy`, `sell`.

Семантика проверена на паре RUB → USD (10.11.2026, курс ЦБ 82,75 RUB за USD):

| Поле | Значение | Смысл |
|---|---|---|
| `DebitCardsTransfers.buy` | 0,011554 | сколько TO банк даёт за 1 FROM, когда клиент покупает TO за FROM: 100 RUB → 1,16 USD, то есть 1 USD обходится в 86,55 RUB |
| `DebitCardsTransfers.sell` | 0,012195 | сколько TO клиент отдаёт за 1 FROM, когда продаёт TO: 1 USD → 82,00 RUB |
| `DebitCardsOperations.buy` | 0,0000291 | оплата картой; для части пар провайдер отдаёт заглушку |

`buy` всегда хуже для клиента, чем `sell` (здесь спред ≈ 5,4 %), а разница `buy` с ЦБ ≈ −4,4 %. Воркер и приложение смотрят на `buy` выбранной категории. Курс оплаты картой отбрасывается, если он отличается от курса обмена более чем в 2 раза (константа `CARD_SANITY_RATIO`): так отсеивается заглушка выше.

TLS-цепочка `api.tinkoff.ru` выдана Russian Trusted Root CA / Russian Trusted Sub CA (Минцифры), которых нет в системных хранилищах. Бандл лежит в `tools/rates/ca/russian_trusted.pem` и подключается только для запросов к провайдеру: контекст `ssl.create_default_context()` плюс `load_verify_locations`, проверка сертификата включена. Сроки: Root CA — до 27.02.2032, **Sub CA — до 06.03.2027**: к этой дате бандл нужно обновить с gu-st.ru. При склейке PEM-файлов между ними обязателен перевод строки, иначе Python не прочитает бандл.

## Центральный банк

`https://www.cbr.ru/scripts/XML_daily.asp` — XML в windows-1251, `Valute` с `CharCode`, `Nominal`, `Value`, `VunitRate` (десятичные через запятую). `VunitRate` — сколько RUB за одну единицу валюты. Курс пары FROM → TO = `VunitRate(FROM) / VunitRate(TO)`, RUB = 1. Курс ЦБ сохраняется в снимке в колонке `cbr` (TO за 1 FROM).

## Формат чисел

Воркер повторяет правила `MoneyFormat` приложения: группировка тысяч неразрывным пробелом, запятая в дробной части, курс через коды валют с обеих сторон («100 RUB = 1,16 USD»), единица масштабируется через `quote_unit` (1 / 10 / 100 / 1 000 …), пока значение не станет ≥ 1. Тесты `tools/rates/test_bank_watch.py` и `MoneyFormatTest` держат оба формата в согласии.

## Настройка

1. Применить миграции `supabase/migrations/0013_bank_rate_watch.sql`, `0014_watch_trigger.sql` и `0015_watch_windows.sql`.
2. Создать бота у [@BotFather](https://t.me/BotFather): `/newbot`, запомнить токен. Токен — секрет, в репозиторий не попадает.
3. Положить токен в секреты GitHub: `gh secret set TELEGRAM_BOT_TOKEN` (значение ввести в интерактивном запросе). `SUPABASE_URL` и `SUPABASE_SERVICE_KEY` уже заведены для курсов.
4. Запустить workflow **Bank rate watch** вручную (Actions → Run workflow) или дождаться крона: воркер вызовет `getMe` и запишет имя бота в `bot_info`.
5. В приложении на экране «Курсы» нажать «Следить за курсом банка», выбрать пару, строгость (верхние 10 / 15 / 25 % недели), порог повтора, часы биржи, необязательный курс «всегда сообщать», сводку и окно отправки.
6. Нажать «Подписаться в Telegram», в боте нажать Start. Ссылку из карточки можно отправить тому, кому ещё нужны уведомления.

Без `TELEGRAM_BOT_TOKEN` воркер завершается с кодом 0 и строкой `TELEGRAM_BOT_TOKEN is not set`, CI остаётся зелёным.

Команды бота: `/start <код>` — подписка на слежение по коду из ссылки, `/stop` — отписка от всех слежений, всё остальное — короткая подсказка.

## Таблицы

| Таблица | Кто пишет | Кто читает |
|---|---|---|
| `bank_rate_snapshots` | воркер (service role) | все залогиненные; вьюха `bank_rate_snapshots_hourly` отдаёт последний снимок каждого часа для графика, замеры недели приложение читает напрямую по `in_hours = true` |
| `rate_watches` | владелец (настройки), воркер (`state`, `link_code`) | владелец |
| `telegram_subscribers` | воркер | владелец слежения читает и удаляет |
| `bot_info` | воркер (`getMe`, offset `getUpdates`) | все залогиненные |
| `exchange_holidays` | миграции, раз в год | воркер, все залогиненные |

## Точный запуск по расписанию

Расписание GitHub Actions в этом репозитории опаздывает на несколько часов, поэтому проверку запускает Supabase: задача pg_cron `bank-watch-dispatch` раз в 15 минут вызывает `public.dispatch_bank_watch()`, а та — `workflow_dispatch` для `bank-watch.yml` через API GitHub (миграция `0014_watch_trigger.sql`). Cron в workflow остаётся запасным.

Настройка (один раз, токен вводит владелец):

1. GitHub → Settings → Developer settings → Fine-grained tokens → Generate: доступ только к этому репозиторию, Repository permissions → Actions: Read and write. Срок — по выбору; при истечении запуски тихо прекращаются.
2. Supabase → SQL Editor:
   ```sql
   select vault.create_secret('<токен>', 'github_dispatch_token');
   ```
   Заменить токен: `select vault.update_secret((select id from vault.secrets where name = 'github_dispatch_token'), '<новый токен>');`
3. Проверить: в GitHub → Actions → Bank rate watch появляются запуски с событием `workflow_dispatch` каждые 15 минут.

Без токена функция ничего не делает.
